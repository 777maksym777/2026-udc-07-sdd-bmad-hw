# Специфікація: Рушій знижок (рівні лояльності + промокоди)

> Головний критерій якості: **два різні інженери (або два прогони агента), що
> реалізують цю специфікацію, мають отримати однакову поведінку.**

**Статус:** agreed
**Джерело:** `materials/feature-request.md`
**Автор рішень:** Maxim (777maxim777)
**Рецензія:** панель BA/SA/Architect (`docs/reviews/`, 2026-09-21) — знахідки
BA-2/SA-3/AR-5 (доля «зʼїденого» купона), AR-1/SA-2в (часова зона й парсинг
`expiresAt`) та SA-1 (нормалізація коду) закриті рішеннями D-15–D-17.

---

## 1. Мета

Після релізу checkout детерміновано рахує знижки: знижка за рівень лояльності
та промокоди (відсоткові й фіксовані, з обмеженнями за категорією та
мінімальною сумою) застосовуються за єдиними, записаними тут правилами.
Будь-який підсумок можна відтворити вручну з цього документа з точністю до
копійки — без здогадок «а що малось на увазі».

## 2. Поза скоупом

Свідомо **не** робимо в цій ітерації:

- UI/тексти повідомлень — рушій лише повертає структуровані причини відмови.
- Зберігання/CRUD промокодів, ліміти використань («один на клієнта», «перші
  100»), генерація кодів. Каталог купонів приходить параметром.
- Безкоштовна доставка як тип знижки; знижки на доставку взагалі (див. D-2).
- Розподіл знижки по рядках замовлення (для бухгалтерії/повернень) — рахуємо
  лише агреговані суми в `PriceBreakdown`.
- Валюти, крім гривні; конвертація.
- Зміни в `app/src/pricing.ts` і `app/src/types.ts` — це стабільний контракт.
- Нормалізація користувацького вводу кодів (trim, регістр) — обовʼязок UI до
  виклику рушія (D-17).

## 3. Рішення щодо неоднозначностей

| # | Питання | Рішення | Чому саме так |
|---|---|---|---|
| D-1 | Промокод і рівень складаються чи застосовуються послідовно? | **Складаються (адитивно)**: кожна знижка рахується від своєї **повної** бази до знижок, потім суми додаються. Gold 10% + промо 15% на 1 000 грн = 250 грн, а не 235 грн. | «Клієнт має відчувати вигоду від обох» — адитивна модель дає рівно те, що обіцяє маркетинг (5% + 10% = 15%). Кожну знижку видно окремо в breakdown, суми звіряються без знання порядку. Маржу захищає кап D-7. |
| D-2 | База знижки — товари чи товари + доставка? | **Лише товари** (`subtotalKopecks`). Доставка додається після всіх знижок і ніколи не зменшується. | Доставка — прохідна собівартість; знижка на неї — окремий продукт («free shipping»), якого тікет не просив. Так `totalKopecks ≥ shippingKopecks` завжди. |
| D-3 | Кілька промокодів — усі / найвигідніший / перший? | **Усі валідні застосовуються**, у порядку введення (`order.coupons`). Один і той самий код удруге — відхиляється як `duplicate`. Два різні коди на одну категорію — обидва застосовуються (кожен від суми категорії). | Тікет прямо каже «клієнт може ввести кілька». Порядок введення вже зафіксовано в типі `Order.coupons` («in the order they typed them»). «Найвигідніший» вимагав би оптимізатора і дивував би користувача, який увів обидва. |
| D-4 | Округлення: де і в який бік? | **Одне округлення на кожну знижку** в момент її обчислення: до найближчої копійки, **пів копійки — вгору** (на користь клієнта). Проміжних дробових значень більше ніде не існує. | Одна точка округлення на знижку ⇒ breakdown завжди сходиться додаванням цілих. «Вгору» на пів копійки — дешевий жест на користь клієнта, який неможливо оскаржити. |
| D-5 | Промокод на категорію рахується від чого? | Від **суми рядків цієї категорії** (до знижок). Відсотковий: `round(catSum × value/100)`. Фіксований: не більше за суму категорії. | «Знижка на fresh» інтуїтивно означає знижку на fresh-товари. Від усього замовлення — це вже звичайний код, категорія втратила б сенс. |
| D-6 | `minSubtotalKopecks` перевіряється до чи після інших знижок? | **До** — проти `subtotalKopecks(order)` без жодних знижок. | Це та сума, яку клієнт бачить у кошику. Перевірка «після» зробила б валідність купона залежною від інших знижок — недетерміновано і незрозуміло користувачу. |
| D-7 | Чи може підсумок стати відʼємним? | **Ні.** Сумарна знижка (рівень + купони) ≤ `subtotal`. Купони застосовуються по черзі: кожен отримує `min(своя сума, залишок бази)`; купон, якому лишається 0, не «застосовується з нулем», а відхиляється (D-15). Товарна частина ≥ 0, отже `total ≥ shipping`. | Магазин не платить клієнту. Кап «по черзі в порядку введення» детермінований і не потребує пропорційного розподілу. |
| D-8 | Прострочений промокод — тиха відмова чи помилка? | **Не помилка і не тиша**: `priceOrder` ніколи не кидає виняток; невалідний купон не впливає на ціну, але потрапляє в `rejectedCoupons` зі структурованою причиною (`expired`, …). | Checkout не має падати через один код. Але «тиха» відмова = скарги в підтримку; причина в breakdown дає UI що показати. |
| D-9 | Код, якого немає в каталозі купонів? | Відхиляється з причиною `unknown`; решта замовлення рахується нормально. | Одруківка користувача — штатна ситуація, не виняток. |
| D-10 | Той самий код введено двічі? | Перше входження працює, друге відхиляється з причиною `duplicate`. | Інакше кожен код — нескінченна знижка. |
| D-11 | Звідки береться «зараз» для перевірки `expiresAt`? | Момент часу `now` — **явний параметр** `priceOrder`. Купон невалідний, коли `now ≥ expiresAt` (за коментарем у `types.ts`: «not valid on or after this instant»). | Чиста функція: детермінований результат, тестується без мокання годинника. Межа «≥» уже зафіксована в контракті типів. |
| D-12 | Купон на категорію, якої в замовленні немає (або сума категорії 0)? | Відхиляється з причиною `not_applicable`. | «Застосований купон зі знижкою 0 грн» — обман очікувань; явна причина чесніша і для UI, і для аналітики. |
| D-13 | Фіксований купон більший за свою базу? | Урізається: `min(value, база категорії або subtotal, залишок за D-7)`. Купон вважається застосованим з урізаною сумою. | Клієнт отримує максимум можливого; відхиляти купон за «занадто щедрий» було б абсурдно. |
| D-14 | Порожнє замовлення (0 товарів)? | `subtotal = 0`, усі знижки 0, купони відхиляються (`not_applicable` / `min_subtotal_not_met`), доставка 0 (наявна поведінка `shippingKopecks`: «усі рядки digital» на порожньому масиві істинне), `total = 0`. Не помилка. | Межовий випадок уже зафіксований наявним тестом `subtotalKopecks` — рушій не має його ламати. |
| D-15 | Купон із непорожньою базою, але вичерпаним залишком (D-7): applied з 0 чи rejected? | **Відхиляється** з причиною `not_applicable`. Загальне правило: якщо фактична знижка `min(номінал, база, залишок)` = 0, купон потрапляє в `rejectedCoupons`; в `appliedCoupons` ніколи немає записів із `discountKopecks = 0`. | Знахідка рецензії (BA-2/SA-3/AR-5): D-7 казав «дає 0», а обґрунтування D-12 називає «застосовано, вигода 0 грн» обманом очікувань — спека суперечила сама собі. Обираємо філософію D-12: applied-список чесний для UI та аналітики, нульові «застосування» не забруднюють статистику промо. |
| D-16 | Як рядок `expiresAt` стає моментом часу? Часова зона? Некоректний рядок? | `expiresAt` валідний лише як повний ISO-8601 момент з явним `Z` або числовим зсувом (напр. `2027-01-01T00:00:00Z`); рушій перевіряє формат і парсить `Date.parse`, порівнює в epoch-мс. Будь-що інше — date-only, date-time без зсуву, сміття на кшталт `not-a-date`, а також **календарно неіснуючий момент** (`2027-02-30`, 29 лютого невисокосного року, година 24) — робить купон невалідним: `rejectedCoupons` з причиною `expired`. Компоненти дати перевіряються до `Date.parse`, бо той мовчки «перекочує» неіснуючі дні на наступний місяць. | Знахідка рецензії (AR-1, SA-2в): `Date.parse` без зсуву дає UTC або локальний час залежно від форми рядка — результат залежав би від TZ машини, що ламає відтворюваність. А `NaN`-порівняння зробило б зіпсований купон вічним; безпечний бік — не дати знижку, а не подарувати її назавжди. |
| D-17 | Нормалізація коду купона (регістр, пробіли)? | **Строге порівняння** `===` з кодом у каталозі; рушій не тримить і не змінює регістр — `save10 ` при каталожному `SAVE10` → `unknown`. Нормалізація вводу — обовʼязок UI до виклику `priceOrder` (поза скоупом, розділ 2). | Знахідка рецензії (SA-1). Рушій детермінований і не вгадує намір користувача; одна точка нормалізації в UI гарантує, що веб і мобілка не розійдуться, а каталог лишається єдиним джерелом істини щодо написання кодів. |

> Питань, на які відповідь «не важливо», не лишилося: кожна розвилка вище
> закрита явним рішенням.

## 4. Критерії приймання

Формат: `AC-N: КОЛИ <ситуація>, ТОДІ <очікувана поведінка>`. Усі суми — цілі
копійки (1 000 грн = 100 000 коп.). Якщо не сказано інше: країна `UA`
(доставка 4 900), `now = 2026-09-21T00:00:00Z`, купони валідні до
`2027-01-01T00:00:00Z`.

- **AC-1:** КОЛИ замовлення на 100 000 коп. від Gold-клієнта без промокодів,
  ТОДІ `tierDiscountKopecks = 10 000`, `couponDiscountKopecks = 0`,
  `totalKopecks = 94 900` (90 000 товари + 4 900 доставка). _(D-1, D-2)_
- **AC-2:** КОЛИ введено купон з `expiresAt = 2026-09-01T00:00:00Z` при
  `now = 2026-09-21T00:00:00Z`, ТОДІ він у `rejectedCoupons` з причиною
  `expired`, знижка від нього 0, функція не кидає виняток. _(D-8, D-11)_
- **AC-3:** КОЛИ в замовленні fresh-товарів на 40 000 і standard на 60 000, а
  введено два купони на категорію fresh — `FRESH10` (10%) і `FRESH15` (15%),
  ТОДІ обидва застосовуються від суми категорії:
  `couponDiscountKopecks = 4 000 + 6 000 = 10 000`. _(D-3, D-5)_
- **AC-4 (граничний):** КОЛИ subtotal = 10 000, tier = none, а фіксований купон
  на 15 000, ТОДІ знижка урізається до 10 000 і
  `totalKopecks = 0 + 4 900 = 4 900` — товарна частина не стає відʼємною.
  _(D-7, D-13)_
- **AC-5:** КОЛИ Gold-клієнт (10%) і купон `SAVE15` (15%, без категорії) на
  замовленні 100 000, ТОДІ знижки адитивні: `10 000 + 15 000 = 25 000`,
  `totalKopecks = 79 900` (а не 23 500 знижки, як було б послідовно). _(D-1)_
- **AC-6 (граничний, пів копійки):** КОЛИ Silver-клієнт (5%) і один товар на
  9 990 коп., ТОДІ 5% = 499,5 коп. округлюється **вгору**:
  `tierDiscountKopecks = 500`, `totalKopecks = 9 990 − 500 + 4 900 = 14 390`.
  _(D-4)_
- **AC-7 (граничний, порожнє замовлення):** КОЛИ `items = []`, tier = gold і
  введено `SAVE15`, ТОДІ `subtotalKopecks = 0`, обидві знижки 0, купон у
  `rejectedCoupons` (`not_applicable`), `shippingKopecks = 0`,
  `totalKopecks = 0`. _(D-14)_
- **AC-8:** КОЛИ subtotal = 50 000, клієнт Gold (знижка 5 000) і купон
  `MIN500` (фіксований 5 000, `minSubtotalKopecks = 50 000`), ТОДІ мінімум
  перевіряється **до** знижок (50 000 ≥ 50 000 — проходить):
  `totalKopecks = 50 000 − 5 000 − 5 000 + 4 900 = 44 900`. _(D-6)_
- **AC-9:** КОЛИ введено `SAVE10` (10%) і `TAKE50` (фіксований 5 000) на
  замовленні 100 000 без рівня, ТОДІ застосовуються **обидва** в порядку
  введення: `couponDiscountKopecks = 10 000 + 5 000 = 15 000`,
  `totalKopecks = 89 900`. _(D-3)_
- **AC-10:** КОЛИ `SAVE10` введено двічі на замовленні 100 000, ТОДІ знижка
  10 000 один раз; друге входження в `rejectedCoupons` з причиною `duplicate`.
  _(D-10)_
- **AC-11:** КОЛИ введено код `NOPE`, якого немає в каталозі, разом із валідним
  `SAVE10` на 100 000, ТОДІ `NOPE` у `rejectedCoupons` (`unknown`), а `SAVE10`
  дає свої 10 000; `totalKopecks = 94 900`. _(D-9)_
- **AC-12 (граничний):** КОЛИ digital-замовлення на 20 000 від Gold-клієнта з
  фіксованим купоном на 30 000, ТОДІ tier = 2 000, купон урізається до залишку
  18 000, `shippingKopecks = 0` і `totalKopecks = 0` — доставка ніколи не
  «зʼїдається» знижкою, а підсумок не відʼємний. _(D-2, D-7)_

- **AC-13 (граничний):** КОЛИ subtotal = 10 000 без рівня, введено фіксований
  купон `TAKE100` (10 000) і слідом `SAVE10` (10%), ТОДІ `TAKE100`
  застосовується на 10 000, а `SAVE10` (база 10 000 > 0, але залишок 0) — у
  `rejectedCoupons` з причиною `not_applicable`; в `appliedCoupons` немає
  записів із `discountKopecks = 0`; `totalKopecks = 0 + 4 900 = 4 900`.
  _(D-7, D-15)_
- **AC-14:** КОЛИ в каталозі купон `BADTIME` з
  `expiresAt = "2026-12-31T23:59"` (без зсуву), `"not-a-date"` або
  `"2027-02-30T00:00:00Z"` (календарно неіснуючий день), ТОДІ він у
  `rejectedCoupons` з причиною `expired` — на будь-якій машині, незалежно від
  її часової зони, і без «перекочування» дати на березень. _(D-16)_
- **AC-15:** КОЛИ в каталозі є `SAVE10` (10%), а користувач ввів `save10`
  (інший регістр) на замовленні 100 000, ТОДІ код у `rejectedCoupons` з
  причиною `unknown`, знижка 0, `totalKopecks = 104 900`. _(D-17)_

Інваріант для всіх AC:
`totalKopecks = subtotalKopecks − tierDiscountKopecks − couponDiscountKopecks + shippingKopecks`,
де `tierDiscountKopecks + couponDiscountKopecks ≤ subtotalKopecks`.

## 5. Контракт

Новий модуль `app/src/discounts.ts`. Типи — з `app/src/types.ts`; наявні
функції `subtotalKopecks`, `shippingKopecks`, `tierPercent` використовуються,
не переписуються.

```ts
import type { Order, Coupon } from "./types.js";

export type CouponRejectionReason =
  | "expired"              // now ≥ expiresAt або некоректний expiresAt (D-8, D-11, D-16)
  | "unknown"              // коду немає в каталозі; порівняння строге === (D-9, D-17)
  | "duplicate"            // той самий код удруге (D-10)
  | "min_subtotal_not_met" // subtotal до знижок < minSubtotalKopecks (D-6)
  | "not_applicable";      // база порожня або фактична знижка 0 (D-12, D-14, D-15)

export interface AppliedCoupon {
  code: string;
  discountKopecks: number; // фактично надана (можливо, урізана за D-7/D-13) сума
}

export interface RejectedCoupon {
  code: string;
  reason: CouponRejectionReason;
}

export interface PriceBreakdown {
  subtotalKopecks: number;
  tierDiscountKopecks: number;
  couponDiscountKopecks: number; // сума по appliedCoupons
  appliedCoupons: AppliedCoupon[];   // у порядку введення
  rejectedCoupons: RejectedCoupon[]; // у порядку введення
  shippingKopecks: number;
  totalKopecks: number; // subtotal − tier − coupons + shipping, ніколи < shipping
}

/**
 * Чиста функція; ніколи не кидає виняток через вміст купонів.
 * @param order    замовлення; order.coupons — коди в порядку введення
 * @param catalog  каталог відомих купонів
 * @param now      момент часу для перевірки expiresAt (D-11)
 */
export function priceOrder(order: Order, catalog: Coupon[], now: Date): PriceBreakdown;
```

Порядок обчислення (нормативний):

1. `subtotal = subtotalKopecks(order)`.
2. `tierDiscount = roundHalfUp(subtotal × tierPercent(order) / 100)` (D-1, D-4).
3. Для кожного коду з `order.coupons` по черзі: пошук у каталозі строгим
   `===` без нормалізації (D-17); валідація (D-9 → D-10 → D-8 → D-6 → D-12;
   фіксується перша причина, що спрацювала; для D-8 рядок `expiresAt` без
   явного зсуву/`Z` або з непарсибельним вмістом одразу дає `expired`, D-16);
   база — сума категорії або subtotal (D-5); номінал —
   `roundHalfUp(база × value/100)` або `value`; фактична знижка —
   `min(номінал, база, залишок)`, де
   `залишок = subtotal − tierDiscount − вже надані купонні знижки` (D-7,
   D-13); якщо фактична знижка = 0 — купон відхиляється з причиною
   `not_applicable`, а не «застосовується з нулем» (D-15).
4. `total = subtotal − tierDiscount − couponDiscount + shippingKopecks(order)`.

`roundHalfUp(x) = Math.round(x)` для невідʼємних значень — єдина точка, де
може виникнути дріб; усе інше — цілочисельна арифметика в копійках.
