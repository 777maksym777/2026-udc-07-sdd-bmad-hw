# Task B — SDD-інструмент: OpenSpec

**Інструмент:** [OpenSpec](https://github.com/Fission-AI/OpenSpec)
(`@fission-ai/openspec`), схема `spec-driven`.
**Чому саме він:** Node CLI без додаткових рантаймів (`uv`/Python не
потрібні) — найдешевший старт для цього репозиторію.

## Що він згенерував

Цикл: `openspec init` → `openspec new change add-discount-engine` →
чотири артефакти за граф-залежностями (proposal → specs + design → tasks) →
`openspec validate add-discount-engine --strict` → зелено.

| Артефакт | Шлях | Зміст |
|---|---|---|
| proposal | `openspec/changes/add-discount-engine/proposal.md` | «навіщо»: проблема, список змін, декларація capability `pricing-discounts`, impact |
| delta-spec | `openspec/changes/add-discount-engine/specs/pricing-discounts/spec.md` | 10 вимог у нормативному форматі `### Requirement` + `#### Scenario` (WHEN/THEN), покривають D-1…D-14 і AC-1…AC-12 з `docs/spec/pricing-discounts.md` |
| design | `openspec/changes/add-discount-engine/design.md` | «як»: 6 технічних рішень з альтернативами (одна чиста функція, валідатор «перша причина перемагає», послідовний fold для капу, `Math.round` як half-up…) |
| tasks | `openspec/changes/add-discount-engine/tasks.md` | 9 чекбоксів у 4 групах, кожен із критерієм перевірки; парсяться командою `openspec apply` для трекінгу |

Сам CLI генерує **скелети й правила**, а зміст пише агент — інструмент за
вас не думає, він структурує.

## Що він дав понад звичайну markdown-специфікацію

1. **Машинну валідацію.** `openspec validate --strict` реально відхиляє
   зміну без дельта-специфікації, вимогу без сценарію, сценарій не на 4
   решітки, закороткий Purpose. Мій `docs/spec/pricing-discounts.md` ніхто
   механічно не перевіряє — тут формат вимог перевіряється як код.
2. **Граф залежностей артефактів.** `openspec status` показує, що tasks
   заблоковані, поки немає specs і design — нав'язує порядок «вимоги → план»,
   який у чистому markdown тримається лише на дисципліні.
3. **Життєвий цикл, а не файл.** Зміна живе в `changes/`, після реалізації
   `openspec archive` вливає дельту в основні specs (`openspec/specs/`) —
   з'являється поняття «поточна правда про систему» окремо від «запланована
   зміна». У markdown-спеки такого стану немає.
4. **Нормативний формат сценаріїв.** WHEN/THEN-сценарії один-до-одного
   лягають у назви тестів — простежуваність (Task C) майже безкоштовна.
5. **Інструкції для агента на кожен крок.** `openspec instructions <artifact>`
   видає контекст, правила й шаблон — два різні прогони агента отримають
   однакову структуру артефактів.

## Що довелося робити руками

- **Увесь зміст.** Розвилки D-1…D-14, рішення, «чому», конкретні числа в
  AC — все це з Task A; OpenSpec лише розклав це по своїх форматах.
  Інструмент не знайшов жодної нової неоднозначності.
- **Перекладання спеки у формат дельти.** Мапінг «рішення → Requirement,
  AC → Scenario» — ручна робота; конвертера немає.
- **Дублювання правди.** Тепер рішення живуть у двох місцях
  (`docs/spec/` і `openspec/changes/.../specs/`) — синхронізацію ніхто не
  перевіряє.

## Чесний висновок

Для фічі на один модуль **основну цінність дала специфікація з Task A, а не
інструмент**: до моменту `openspec new change` усі рішення вже були прийняті.
OpenSpec додав перевірюваний формат, порядок артефактів і життєвий цикл
дельта-спек — це стане відчутним на проєкті з багатьма змінами й багатьма
авторами, а на цьому обсязі це ~20 хвилин перекладання готових рішень в іншу
розкладку. Тобто: інструмент корисний як **рейки для агента і команди**, але
він не замінює і не прискорює саме мислення над розвилками.
