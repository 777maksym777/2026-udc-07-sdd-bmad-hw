> Дата: 2026-09-21 · Хост: Claude Code / Fable 5

## Рецензія Architect

Вердикт: **approve-with-comments**

---

**AR-1** **[severity: major]** — D-11, контракт (`expiresAt`), ризик №4.
Спека фіксує межу `now ≥ expiresAt`, але не фіксує, **як рядок стає моментом часу**. `Coupon.expiresAt` — ISO-рядок, а в JS `Date.parse` для `"2027-01-01"` дає UTC, а для `"2027-01-01T00:00"` (без зсуву) — локальний час сервера. Той самий каталог + той самий `now` → різний результат залежно від TZ машини, що прямо ламає головний критерій «два прогони — однакова поведінка». Ціна зараз: одне речення («`expiresAt` завжди містить зсув/`Z`; парсинг — `Date.parse`») плюс граничний AC. Ціна потім: невідтворюваний прод-баг «купон працює на стейджі й мертвий на проді» рівно опівночі.

**AR-2** **[severity: major]** — D-10 проти нормативного порядку (розділ 5).
Порядок валідації `D-9 → D-10 → …` означає «duplicate = код уже *зустрічався* в списку», а формулювання D-10 «перше входження **працює**, друге відхиляється» означає «duplicate = код уже *застосувався*». На вході `["EXPIRED", "EXPIRED"]` перший прочитаний варіант дає `[expired, duplicate]`, другий — `[expired, expired]`. Показово, що робоча реалізація вже розійшлась зі спекою третім способом: вона позначає код «використаним» *до* перевірки каталогу, тож другий `NOPE` стає `duplicate`, хоча за порядком розділу 5 має бути `unknown`. Ціна зараз: одне уточнююче речення + AC. Ціна потім: розбіжні тести двох реалізацій і суперечка «хто правий», яку спека мала закрити.

**AR-3** **[severity: minor]** — контракт, `AppliedCoupon`; D-7/D-13, споживач «аналітика/бухгалтерія».
`discountKopecks` — уже урізана сума, і breakdown-ом сходиться (добре). Але після урізання ніхто не відрізнить «купон на 30 000 дав 18 000, бо вперся в залишок» від «купон і був на 18 000». Для аналітики ефективності промо і для підтримки («чому мені не всі 300 грн?») це перше, чого попросять. Додати `nominalKopecks` (або `cappedBy`) потім — неламке розширення, тож це не блокер; але зараз це один рядок у інтерфейсі, а потім — бекфіл історичних даних, який зробити вже неможливо.

**AR-4** **[severity: minor]** — контракт, `CouponRejectionReason`; еволюція (ліміти використань).
Розділ 2 сам прогнозує ліміти («один на клієнта», «перші 100») — це гарантовано нова причина відмови, наприклад `usage_limit_reached`. Закритий union + exhaustive `switch` у споживачів = кожне нове значення ламає UI/аналітику компіляційно або, гірше, у рантаймі. Ціна зараз: одне речення «споживачі зобовʼязані трактувати невідому причину як загальну відмову; перелік відкритий для розширення». Ціна потім: координований реліз рушія і всіх споживачів заради одного рядка enum-а.

**AR-5** **[severity: minor]** — D-7 проти D-12; контракт `appliedCoupons`.
D-7: «коли залишок 0, наступні дають 0» — тобто купон *застосований* зі знижкою 0. D-12 відхиляє купон із порожньою базою саме тому, що «застосований купон зі знижкою 0 грн — обман очікувань». Філософії суперечать, і спека не каже явно, куди потрапляє «зʼїдений залишком» купон — в `appliedCoupons` з нулем чи в `rejectedCoupons` (і з якою причиною — наявні пʼять не підходять). Третій купон поверх сценарію AC-12 — і дві реалізації розійдуться. Одне речення зараз проти нового D-рішення заднім числом потім.

**AR-6** **[severity: nit]** — контракт, `catalog: Coupon[]`; ризик O(n·m).
Спека не каже, що робити з каталогом, де два купони мають один `code` (перший виграє? помилка даних?). Лінійний `find` по каталогу при 2–3 введених кодах — не проблема продуктивності на checkout, міняти сигнатуру на `Map` не треба; але правило «перший збіг за кодом» варто промовити одним рядком, інакше це прихована залежність від порядку масиву.

**AR-7** **[severity: nit]** — розділ 5, `roundHalfUp` / переповнення.
Пін `roundHalfUp = Math.round` для невідʼємних — коректний і достатній (для відʼємних `Math.round` — це half-up у бік +∞, але спека явно обмежилась невідʼємними: добре). Переповнення нереальне: цілі копійки в JS точні до 2^53 ≈ 90 трлн грн; `база × value` цього не наблизить. Жодних дій не потрібно — фіксую лише, що ризик перевірено і він порожній.

Окремо, що **не** є блокером (перевірено за п. 3): free shipping потім додається полем `shippingDiscountKopecks` без зламу наявних полів (доведеться лише послабити коментар-інваріант `total ≥ shipping` у `totalKopecks`); розподіл по рядках — окреме обчислення поверх тих самих рішень D-4/D-5; чистота `priceOrder(order, catalog, now)` сумісна з лімітами використань, якщо стан прийде через каталог. Інтеграція чиста: `subtotalKopecks`, `shippingKopecks`, `tierPercent` використовуються as-is, розділ 5 реалізовний як чиста функція без зміни `pricing.ts`.

---

**Найцінніша знахідка:** AR-1 (парсинг `expiresAt` без зафіксованої часової зони) — **реальна**: це єдине місце, де спека, що обіцяє побайтову відтворюваність, залежить від налаштувань машини, і воно не покрите жодним AC.
